## Problem

An agent that acts on real systems will sooner or later propose something it should not do. A coding agent fixing a failing test might sensibly run `git status`, reasonably want to `npm install` a new package, and, after reading a hostile comment in the code, try `rm -rf /`. Asking a person to approve every call makes the agent too slow to be worth using, and approving none of them trusts the model with everything it can reach. A sentence in the system prompt saying "never delete files" is a request, not a limit.

## How it works

Put a <NodeRef id="policy">policy</NodeRef> between the <NodeRef id="agent">agent</NodeRef> and its tools. The policy is plain code reading declarative rules, so the model cannot argue with it. Every proposed call is matched against three lists, checked in a fixed order: deny first, then ask, then allow. The order matters, because it means a broad allow rule can never override a specific deny.

In the example, `git status` matches an allow rule and goes straight to the <NodeRef id="tool">shell</NodeRef>; nobody is bothered. `npm install date-fns@4` matches an ask rule, so the policy sends it to the <NodeRef id="human">developer</NodeRef> with the agent's reason, and it runs only after they approve. `rm -rf /` matches a deny rule. It never runs, and the agent gets an error naming the rule, so it can pick another approach instead of retrying the same one. A call that matches no rule at all is treated as ask, never allow.

The policy also keeps a budget meter. Each call adds its cost and counts as a step. When the next call would pass the cap, here $2, the policy ends the run and sends a stop report to the <NodeRef id="out">result</NodeRef> instead of running it. Every decision goes into an audit log: the call, the rule it matched, the verdict and who approved it.

## When to use

- The agent acts on real systems: files, repositories, cloud accounts, money, messages to people.
- You want predictable, reviewable limits without a person approving every call.
- Different calls carry very different risk, so one blanket rule would be either too loose or too strict.

## When to avoid

- The tools are pure read-only lookups. The overhead buys nothing.
- Every action is high-stakes. Then you need a person on every call, which is plain human-in-the-loop.
- You cannot describe the risky calls as rules over tool names and arguments. A rule list that is mostly exceptions will be wrong in both directions.

## Trade-offs

A policy makes autonomy auditable, but only as good as its rules. Rules written too tight bury the developer in ask prompts, and people who are asked too often start approving without reading. Rules written too loose let through the call nobody thought of. Matching on arguments is harder than it looks: a shell command can hide a second command after a semicolon, so match on parsed calls, not raw text. The policy itself adds almost no latency; the ask lane adds as much as the person takes to answer.

## Failure modes

- **Rule bypass:** the agent reaches a denied effect another way, such as writing a script that does what the denied command would. Deny by effect where you can, and pair the policy with a sandbox.
- **Approval fatigue:** the ask lane fires so often that the developer approves everything. Move safe, frequent calls to allow, and keep ask for the few that matter.
- **Retry storms:** the agent keeps rephrasing a denied call. Tell it, in the prompt and in the error, not to retry denied calls, and count denials toward the step cap.
- **Silent defaults:** a new tool with no rule is allowed by mistake. Default to ask.

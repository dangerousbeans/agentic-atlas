## Problem

Some tasks need several specialists who react to each other. Planning "a 3-day Tokyo trip for under $1,500" takes someone to draft the days, someone who knows the city, and someone who keeps the total honest. Nobody can say in advance whose turn comes next: whether the planner speaks again depends on whether the budget checker just found an overrun. A fixed pipeline guesses the order wrong, and a supervisor that collects results privately means the specialists never hear each other.

## How it works

All the agents share one conversation. The task is posted as the first message of the <NodeRef id="thread">shared thread</NodeRef>. Each turn, the <NodeRef id="manager">chat manager</NodeRef> reads the whole thread and picks one speaker. It is usually a cheap model call given the agents' role descriptions, but it can be a simple rule. The chosen agent is called with the full thread, and its reply is appended for everyone to see.

In the example, the manager first calls on the <NodeRef id="planner">planner</NodeRef>, which drafts an itinerary. It then picks the <NodeRef id="budget">budget checker</NodeRef>, which prices the plan and posts "over by $200". Because that message is in the shared thread, the manager sends the turn back to the planner, which swaps to a cheaper hotel without anyone relaying the problem. The <NodeRef id="local">local expert</NodeRef> is there whenever the conversation needs it. When the thread answers the task, the manager says TERMINATE and the latest plan goes to the <NodeRef id="out">output</NodeRef>.

The manager never writes content. It only chooses who talks, so all the actual work lives in the agents' messages.

## When to use

- Several roles need to see and respond to each other's contributions.
- The right speaking order depends on what was just said and cannot be fixed in advance.
- You want a conversation you can read afterwards: the thread is a complete, attributed record of who said what.

## When to avoid

- The order is known. A fixed sequence such as an SOP-driven team or prompt chaining is cheaper and easier to test.
- You have many agents or long messages. Every agent rereads the whole thread every turn, so the context grows quickly.
- The work splits into independent pieces. Running them in parallel and combining the results is faster than taking turns.

## Trade-offs

Each turn costs two model calls, one to select the speaker and one for the speaker itself, and every call carries the whole growing thread. The cost climbs faster than the number of turns. In exchange you get flexible coordination with very little orchestration code: adding a role means adding a participant and a one-line description for the selector. Behaviour is harder to predict than a fixed pipeline, because the selector can choose a different order on every run.

## Failure modes

- **Endless chatter:** agents keep agreeing or politely re-litigating, and nobody says TERMINATE. Always cap the turns, and return the thread with a clear status when the cap is hit.
- **Bad speaker choice:** the selector picks the same agent repeatedly, or names one that does not exist. Validate the name, block back-to-back repeats, and fall back to a rotation.
- **Impersonation:** an agent writes lines for other participants. Tell each one to speak only for itself, and cut its reply at another speaker's name.
- **Context blow-up:** the shared thread outgrows the context window. Trim the oldest replies or summarise them, but always keep the original task.

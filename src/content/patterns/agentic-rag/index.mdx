## Problem

Classic retrieval-augmented generation always retrieves once, from one index, using the user's raw question. That fails in three ways. Some questions need no retrieval at all. Some need a different source, such as a SQL table of orders instead of a wiki. And some need several lookups, where the first result tells you what to ask next.

## How it works

Hand retrieval to an <NodeRef id="agent">agent</NodeRef> as a set of tools. On each hop the agent reads the <NodeRef id="user">question</NodeRef> and everything gathered so far, then chooses one of two moves: answer, or search. A search names a source and a query rewritten for that source. A <NodeRef id="router">source router</NodeRef> sends it to the <NodeRef id="vectordb">vector database</NodeRef> for internal documents, to <NodeRef id="web">web search</NodeRef> for fresh facts, or to <NodeRef id="sql">SQL</NodeRef> for structured records.

Whatever comes back is appended to the agent's context and the loop runs again. A question like "Did our refund policy change after the March incident?" might hit the vector database for the policy, find that the chunks predate March, then query the web or an incident log with a sharper question. When the agent judges the context sufficient, it writes the <NodeRef id="out">answer</NodeRef> with citations.

## When to use

- Questions span several knowledge sources with different strengths.
- A single query rarely finds everything, so follow-up searches matter.
- Many questions need no retrieval, and you want to skip the cost on those.

## When to avoid

- One well-tuned index answers nearly everything. Plain RAG is cheaper and easier to debug.
- You need predictable latency. The number of hops varies per question.
- The agent has no way to tell good context from bad. Add a grader, as in Corrective RAG.

## Trade-offs

Each hop is a model call plus a search, so latency and cost grow with the hop count and vary per question. In exchange you get better recall and the ability to cover several sources. The agent's tool descriptions become part of your retrieval quality: vague source descriptions produce wrong routing.

## Failure modes

- **Over-searching:** the agent keeps retrieving when it already has enough. Cap the hops and force an answer at the cap.
- **Under-searching:** it answers from memory when it should have looked. Instruct it to cite context, and reject uncited factual claims.
- **Query drift:** each rewrite wanders from the original intent. Keep the original question in every prompt.
- **Wrong source:** it queries SQL for something that lives in docs. Describe each source's contents and limits precisely.
